# Agent self-check and user result

Check only this screen and its required owned product families. Before reusing a
new source, verify its public API/default/order, actual variants, linked native
dependencies, token/style bindings, true Slot backings/settings/validity and
settled geometry. These checks are performed by the constructing agent itself;
there is no separate source-acceptance turn, Codex reviewer or evidence receipt.

For each actual screen mode, check shell/source identity, mode and selector,
complete specified copy, exact icon/status identity, current Image paints where
used, consumer APIs/Slots and content fit. For Dashboard md/lg check equal FLEX
Grid columns, HUG rows, linked cards FILL/HUG with minWidth224, single-cell spans,
an empty final cell and clipsContent=false. For Sign In check centered full
paragraphs, legal ranges, safe content-driven height and no clipping. Check bound
Section fills, stroke colors/widths and corners after presentation. Capture an
overview screenshot when supported; do not claim visual or interactive behavior
from API fields alone.

Check that file recognition and the usable color-variable/text-style foundation
gate completed before writes; the selected role bindings/styles must be actual.
A delivery package version changing alone is not a reason to reject a compatible
existing source. Check its actual current relevant contract and owned state.
No real hyperlinks or functioning OAuth, clipboard or navigation are required;
check the specified inert link-style copy and appearance instead.
For an explicitly
adapted build, keep that qualification in the result, disclose deviations from
the Sambl reference and never claim verified Sambl compatibility or nonexistent
token bindings. The canonical completion examples below apply to recognized kits.

When complete, say for example: “Sign In is ready on the Examples page. You can
view the screen and its components.” / “Sign In готов на странице Examples.
Можно посмотреть экран и его компоненты.” Include native links to the generated
screen row/root and Product Components when available. State which actual modes
were created. Invite the user to view the result; no mandatory acceptance button.

Show a short separate list only for real issues or substitutions: what could not
be found, what replaced it, what remained unchecked or could not be completed.
Do not show report JSON, hashes, technical artifact keys or invented successful
checks. Compatible substitutions can finish with warnings when all required
semantics and behavior are satisfied. If a required part failed or execution
was interrupted, explicitly identify completed and missing work with review
links; never label unfinished output done. Do not request a final MCP report,
independent validation or automatic retry. Another screen needs a user request.
